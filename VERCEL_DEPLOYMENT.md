# Vercel deployment preparation

The root `vercel.json` exposes the Next.js frontend at `/` and the Express API at `/api/*`; Express keeps its `/api/v1` prefix. The browser calls `/api/v1` on the same origin in production. There are no server-to-server calls between these services, so no service bindings are required. `NEXT_PUBLIC_API_URL` should be unset for the same-origin configuration; for standalone local development, frontend `.env` may keep the existing backend address.

Before enabling any deployment, set `DATABASE_URL`, `JWT_SECRET`, and `JWT_REFRESH_SECRET` as Vercel environment variables for each intended environment. Set `JWT_ACCESS_SECRET` if a separate access signing secret is desired. `API_PREFIX` must be `/api/v1` or unset. Existing non-Vercel browser origins can be supplied in `CORS_ORIGIN`, comma-separated. Do not place secrets in source control. Configure separate preview and production databases or otherwise prevent previews from modifying production data. Database schema provisioning and seed credentials are separate administrative operations; builds do not run migrations or seeds.

**Media storage is not deployment-ready.** The backend currently stores uploaded images and videos in `backend/data/catalogue-media` on the machine running it. Vercel Functions have a read-only, ephemeral filesystem. Existing local photos will not be available on Vercel, and new uploads cannot be persisted. Do not deploy for real users until authenticated durable object storage and a migration of existing photos have been designed and verified. Vercel Functions also limit request and response payloads to 4.5 MB, below the application's current photo and video limits; large files need direct-to-object-storage uploads and downloads.

To validate routing, install an up-to-date Vercel CLI and run `NEXT_PUBLIC_API_URL=/api/v1 vercel dev` from the repository root (this overrides the local frontend `.env` backend URL) after linking an appropriate Vercel project and configuring test environment variables. Verify `/api/v1/health`, sign-in, product listing, access control, and a complete media upload/download workflow using a separate test database and durable test storage. Deployment setup and media migration require separate confirmation.
